Первое сравнение воспроизводит `node scripts/benchmark-cpu.mjs`. В обоих циклах были одинаковые 200000 ID и matcher `_FURRY` с точным регистром; совпадений не было. Ускорение около 2,92 раза относится к циклу ID.

Скорость полного восьмипоточного поиска включала генерацию новых TON-фраз через каждые 1048576 ID на поток. Этот режим выключен в текущем интерфейсе из-за требования обычного импорта в Tonkeeper. Его результат нельзя выдавать за скорость текущего режима.

В BIP39-режиме каждый адрес включает новую случайную 12-словную фразу, PBKDF2-HMAC-SHA512 2048, SLIP-0010, Ed25519 и StateInit. Отбрасываются неоднозначные победители TON/BIP39. Сотни тысяч совместимых адресов в секунду на CPU не достигнуты. Последующие параллельные замеры приведены ниже.

На этапе первоначальных CPU-замеров GPU был отключён. Впоследствии добавлены отдельные режимы GPU и CPU + GPU с порциями и паузами; актуальные GPU-проверки описаны в GPU-THROTTLING.md. Импорт в установленный Tonkeeper не выполнялся; проверены официальная схема и независимое восстановление адреса из сгенерированных слов.
## Исправление масштабирования CPU

Обнаружено ограничение Chromium: медленные операции WebCrypto, включая PBKDF2, обслуживаются общей очередью с одним worker_thread. Размножение Web Workers не создаёт отдельную очередь WebCrypto для каждого из них. [Исходник Chromium, CryptoThreadPool](https://chromium.googlesource.com/chromium/src/+/HEAD/components/webcrypto/webcrypto_impl.cc).

Для BIP39-12 теперь используется локальный PBKDF2-HMAC-SHA512 на уже включённой libsodium/WASM. У каждого вычислительного worker собственный экземпляр WASM. На одном потоке остаётся более быстрый native WebCrypto; при нескольких потоках используется локальный расчёт. Параметры BIP39, стандартный walletID и пути Tonkeeper не меняются. Проверка победителя по-прежнему использует отдельный canonical WebCrypto/TON SDK путь.

Новые измерения полного пути с новыми BIP39-фразами, standard V4R2 ID и matcher:

| --- | ---: | ---: |
| Node, прежний WebCrypto | 1 | 363 |

| Node, локальный WASM | 4 | 861 |

`node scripts/benchmark-parallel.mjs` воспроизводит Node-замеры. Каждый worker прогревается четырьмя одноразовыми фразами, затем проверяет 128 новых адресов; сумма делится на общее время одновременной работы. Секреты не выводятся и не сохраняются. Кнопка замера в интерфейсе также измеряет суммарную скорость выбранного количества потоков после прогрева, а не умножает однопоточное значение.

Сотни тысяч совместимых адресов/сек пока не достигнуты. Улучшение устраняет общую очередь и не заменяет PBKDF2 более слабой схемой.
Браузерный замер 16 потоков: 1898 адресов/сек (2048 новых BIP39-фраз после прогрева). 8 потоков: 1622 адресов/сек. Это CPU-замеры до добавления совместного режима. Теперь XOR накопителя PBKDF2 выполняется 16 словами uint32 вместо 64 отдельных байтов; независимые OpenSSL-векторы проходят. Ползунок использует hardwareConcurrency (на этом устройстве 24), прежний предел 16 убран.
